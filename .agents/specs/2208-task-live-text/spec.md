# Live co-editing of a task's title and description

Technical translation of Epic #2208. Written against `origin/main` at `e7b06aec` (2026-11-16); every line reference in [plan.md](./plan.md) is pinned to that commit. It builds on two specs that are still in review: assignees and the task change set (#2172, PR #2175, `.agents/specs/2172-task-assignees/` on branch `docs/2172-task-assignees`) and task threads with the activity log (#2173, PR #2178, `.agents/specs/2173-task-threads/` on branch `docs/2173-task-threads`).

Product decisions (2026-11-16): the description stays **plain text** (no Markdown, no rich-text formatting), and **both** the title and the description are co-edited live with Yjs and remote carets, the way Notes does it.

## Goal

- **One room per task, two plain-text fields.** A task's room holds one Yjs document with two `Y.Text` shared types:
  - `note-title`: the title type Notes already uses (`NOTE_TITLE_YTEXT_KEY`). The key name stays; it is the suite's "title of a collab document" type, not a Notes-only one;
  - `plain-body`: a new type for a plain-text body.

  There is no TipTap editor and no `Y.XmlFragment`. Both fields stay the textareas they are today. They bind to their `Y.Text` with the binding and the remote-caret overlay the Notes title already has (`useNoteTitleField`, `useNoteTitleCarets`, the textarea mirror geometry), generalised to take a key. The caret geometry already wraps over several lines, because the Notes title is a textarea.
- **The same collab stack as Notes, no second one.** The room is joined through the existing `/rooms` signaling, synced over the RTC mesh between browsers (TURN only when peers cannot connect directly), and saved over REST by the shared save loop (`persistCollabSave`, the same 2 s debounce and 3 s cap). The server runs no Yjs. The shared session gets a third document shape next to Docs (`default` fragment) and Notes (fragment + title): **text fields only**, so it can seed, save and rebuild without mounting TipTap.
- **The VTODO is the document of record.** `SUMMARY` and `DESCRIPTION` are what every client reads, ours included. The server also stores the last saved Yjs state of each co-edited task (`task_yjs_state`), the same way Notes stores `note_yjs_state`. That state is never shown to anyone. It is the merge base that lets live peers, tabs and offline devices agree on one history.
- **An outside edit never prompts.** Native clients (Apple Reminders, Thunderbird, jtx Board, tasks.org through DAVx5), MCP `task_write` and a plain REST `PATCH` change `SUMMARY` or `DESCRIPTION` without touching the stored state. Notes asks the person in that case when they have unsaved work (Decision 6 of `docs/architecture/notes.md`); for tasks that prompt would show all the time. Tasks always merges:
  - The server keeps an **outside chain** next to the stored state: every text an outside write left since that state was saved, in order. Every client turns the chain into **the same deterministic Yjs updates**, one per link, each the diff from the previous link's text (the stored state's text for the first) to that link's text, written in a throwaway document that already holds the stored state and the earlier links. Two peers or two tabs that apply a link produce byte-identical items, so the second application is a no-op, and a peer that missed an earlier link replays it from the chain first. Typing made after the stored state merges with them by the CRDT.
  - When there is no shared state to diff from (the task was never co-edited, a move dropped the state, or the state was compacted), the first save wins with `If-None-Match: *` and every other client **rebases** onto the winner with a three-way merge of plain text (see Technical constraints, Reconcile). Nobody is asked.
- **Text edits leave the task outbox.** While the live API is on, the detail view never sends `title` or `description` in a task `PATCH` for a task that exists on the server. Offline, the text lives in the room's Yjs document in IndexedDB (the y-indexeddb buffer Notes uses) and saves when the connection is back, merged as above. Creating a task still sends its first title in the create `POST`, and a task whose create is still queued keeps editing through that create (Edge cases).
- **Metadata writes keep working while people type.** A text save changes the object ETag every few seconds. A status, due, priority, alarm, move or assignee write from the autosave or the outbox would then hit `412` and show an error. A `412` on a patch whose fields the server did not change since the client's base is retried once with the server's ETag, with no dialog and no error.
- **The activity log does not flood.** Each person saves at most every ~3 s while typing. Epic #2173 merges quick edits by the **same** actor on the same field within 10 minutes, but only into the newest entry of the thread, so two people typing in turn would still add one entry per save. For `title` and `description` only, this Epic changes the merge into a **cross-actor** merge (Technical constraints, Activity log). Title and description changes notify nobody, as #2173 already decides.
- **Access.** Joining a task room needs read access to the task's list. The peer's right is `write` only with write access to the list; a read-only viewer sees the typing and the carets, cannot type, and publishes no caret. Losing access mid-session ends the session (the signaling re-check that exists today), and unsaved text is parked for the existing Tasks rescue flow instead of being lost.

## Non-goals

- Markdown or rich text in the description, a toolbar, or formatting shortcuts
- Live co-editing of status, due, priority, alarms, tags, assignees or the list. They keep their autosave and outbox.
- Presence in the task list (who has a task open)
- A server-side Yjs process, a websocket relay or a server-side merge
- Live typing inside native clients. They see the text once it is saved and they sync.
- Co-editing in mock mode and Storybook. Without the live API the detail view keeps the solo autosave it has today.
- Changing how Notes handles outside writes. Notes keeps its prompt (Decision 6).
- Co-editing a task from MCP. MCP writes stay plain REST writes, which the room treats as outside writes.

## Technical constraints

### Room key and join

- The REST task id is the object URI, or `{objectUri}#{vtodoUid}` for a VTODO inside a multi-VTODO file (Decision 9 of `docs/architecture/tasks.md`). `findOwnedTask` resolves it by URI across every list the caller can reach. A URI is chosen by whichever client created the object, so two unrelated lists can hold the same URI. The task id is therefore **not** a safe room key: someone could create a task with the URI of a task they can no longer see, join that room, and receive its live text.
- The room key is `task:<calendarid>:<vtodo-uid>`, built by the server. `calendarid` is the shared calendar row, the same for the owner and every sharee; the UID names the component. The client gets it from `GET /tasks/items/{taskId}/text` and never builds it.
- **Parsing the key.** The literal prefix `task:`, then a decimal `calendarid` (digits only), then one `:`, then **the whole remainder** as the UID. UIDs the server mints are `urn:uuid:…` (`TaskRepository.php:507`), and native clients may use colons too, so the key is never split on every colon. A key without digits after the prefix, or with an empty UID, is `403`.
- `CollabJoinAuthorizer::assertMayJoin` and `accessFor` check the `task:` prefix **before** the "a slash means a Drive path" test, because a VTODO UID written by a native client may contain a slash. A task room resolves to the VTODO with that UID in that calendar, then to the caller's accessible instance on that calendar (`CalendarCollectionAccess`, the same lookup the task routes use, dismissed and hidden shares excluded). No such object, or no instance: `403`. Access is `write` when the instance is writable, `read` otherwise.
- A note whose UID starts with `task:` can no longer open a room. Notes created by the app have UUIDs; a foreign journal with that UID is not a supported case (Decision 17 of `notes.md`).
- The rest of the join is unchanged: the per-poll re-check (`assertStillMayJoin`) ends the session when read access goes away, `refreshAccess` narrows the ticket when write access goes, `MAX_PEERS_PER_ROOM` stays 20, and peers drop updates from a peer whose ticket says `read`.

### Stored state

- `task_yjs_state`: `id`, `calendar_object_id` (FK to `calendarobjects.id`, `ON DELETE CASCADE`), `vtodo_uid` (the component's real `UID`, also for a single-VTODO object, so the row still matches after a native client adds a second VTODO and the REST id becomes `uri#uid`), `state` (binary; widened to `MEDIUMBLOB` on MySQL as the `note_yjs_state` migration does, because Laravel's `binary()` is a 64 KiB `BLOB` and the cap below is 256 KiB), `object_etag`, `content_etag`, `outside_chain` (JSON, see below), timestamps. Unique `(calendar_object_id, vtodo_uid)`. Otherwise the same shape and rules as `note_yjs_state`.
- `content_etag` is `sha1(description . "\0" . title)` of the text **the stored state holds**. A metadata write (status, due, assignee, alarm) changes `object_etag` and leaves the text alone, so it is not an outside write.
- **The outside chain.** `outside_chain` is an ordered list of `{contentTag, title, description}`, at most 20 links. A link holds a text that reached `SUMMARY` or `DESCRIPTION` by any path other than the text `PUT` while a state row exists: REST `PATCH`/`PUT`, MCP, and CalDAV `PUT`. Task import is not a source: it only creates objects and refuses an existing UID with `409 already_exists`. A text `PUT` that stores a new state clears the chain. When the chain would pass 20 links, the server drops the state row instead; every client then takes the rebase path.
- **The chain's end.** "The text the room is based on" is the last link's content tag when the chain is not empty, and the state row's `content_etag` when it is. Every rule below compares with that one tag, never with "the state or the chain".
- **One lock for every write to a task object.** Each change to the chain and each task write runs in one `wgw` transaction that first does `lockForUpdate()` on the `calendarobjects` row and then on its `task_yjs_state` row, and re-reads both:
  - **Every `rewriteOwnedTask` write** (REST `PATCH` and `PUT`, MCP, move) checks `If-Match` on the **locked** row, not on the unlocked read it does today (`TaskRepository.php:293`), builds the ICS from the locked read, writes it, and, when the text changed and a state row exists, appends the new text as a link before it commits. The text `PUT` is the one caller that does not append: it passes a flag, because it stores a new state instead. A `PATCH` that read the object before a text `PUT` and reaches its write after it therefore gets `412` and writes nothing; it no longer reverts the saved text. Sabre's `updateCalendarObject` has no predicate on the old ETag, so only this lock prevents that.
  - **CalDAV `PUT`** (an `afterMethod:PUT` hook on task-list objects with a 2xx status; #2172's `TaskChangeObserverPlugin` once it is on main, a small plugin of this Epic before that) appends **the text of its own request body** under the same locks, and only when that text's content tag is not already the chain's end. Two native `PUT`s whose hooks run in order leave both links in order. Hooks can also finish in another order than the commits, or run only after both commits; then the chain may not end on the object's text, but nothing is doubled, and the locked `?format=yjs` repair or the text `PUT`'s `409` appends the object's text so the chain ends on it. A conditional native `PUT` (`If-Match`) is checked by Sabre before its own unlocked write; that race between a native client and our write is Sabre's and exists today for any two writers. An unconditional native `PUT` stays last-write-wins for the body it sent.
  - **`GET …?format=yjs` repair:** when the object's content tag is not the chain's end, the read appends it as a link under the same locks, after re-reading both rows. A read that started before a text `PUT` and reaches its append after that `PUT` committed re-reads, finds the object at the new chain's end, and appends nothing.
  - Overlapping appends serialise on the state row's lock, so no append is lost or doubled. The order of links follows the order the hooks run (see CalDAV `PUT` above); the locked repair makes the chain end on the object's text.
- A move through REST creates the object in the target calendar and deletes it from the source (`TaskRepository.php:321`), and a CalDAV `MOVE` does the same. The new object has a new `calendarobjects.id`, so the state row is gone with the old one. The room key changes too (new `calendarid`). This is intended: the next join seeds from the text, and any client with unsaved text rebases.
- Size: the stored state is capped at 256 KiB (`413 state_too_large`). Title and description stay capped at 4 096 and 8 192 characters, as in `TaskPatchRequest`. A plain-text Yjs state at those sizes stays far below the cap unless a long history of deletions accumulates; then a client that is alone in the room compacts: it seeds a new document from the current text and saves it with `If-Match` on the old tag.

### API

New sub-resource under the existing `wgw.tasks` middleware group. `{taskId}` is the REST task id.

- `GET /api/v1/tasks/items/{taskId}/text` returns `{ title, description, room, stateTag, outsideChain }` with `ETag` set to the **content tag** of the current object. `stateTag` is the tag of the stored state the chain belongs to (null without a row); `outsideChain` is the ordered list of `{contentTag, title, description}` (empty without a row). A client that read a different state tag from `?format=yjs` reads both again. Read access to the list.
- `GET /api/v1/tasks/items/{taskId}/text?format=yjs` returns the stored state bytes with `ETag` set to the state tag (`DocCollabDocumentService::sidecarEtag`). When the chain is not empty it sets `X-Wgw-External-Write: 1`, as Notes does. No row: `204` (the client seeds from the text). Read access.
- `PUT /api/v1/tasks/items/{taskId}/text`: the framed payload Notes uses (`FramedPayload`: `documentLen`, `yjsLen`, optional `title`), where the document part is the description. Write access to the list.
  - `If-Match` on the state tag, or `If-None-Match: *` when the client saw no state. No precondition while a state exists: `428`. A mismatch: `412`.
  - **A first save** (no state row, `If-None-Match: *`) must name in `X-Wgw-External-Write` the content tag it seeded or rebased from: the `ETag` of the `GET …/text` it read. Under the lock, if the object's content tag differs from that tag (Reminders wrote between that read and this save), it answers `409 external_write` and writes nothing; the client re-reads and takes the no-state rebase (Reconcile). Without this, every task's first save, and the first save after a move, could write over a native edit, because there is no chain yet to compare with.
  - **Under the lock**, a save with a state row compares the locked object's content tag with the chain's end. If they differ (a native `PUT` committed but its hook has not run yet), it appends that text as a link, commits the link, and answers `409 external_write` without writing. Otherwise, while the chain is not empty, the save must name the last link's tag in `X-Wgw-External-Write`, or it gets `409 external_write`. This is the guard `NoteCollaborativeWrite::assertNoUnseenExternalWrite` already has, keyed on the chain's end; it proves the client merged every outside text before writing over it.
  - **Locked write.** The text `PUT` takes the locks above (as `NoteCollaborativeWrite::put` does for notes), re-reads the ICS from the locked row, checks the state precondition and the chain guard, builds the new ICS **from the locked read**, writes the object and writes the state row. `rewriteOwnedTask` takes the locked object as input for every caller (spec above); the text `PUT` skips only the object `If-Match`, because the state tag is its precondition.
  - The text is applied as a patch of `title` and `description` (`""` removes `DESCRIPTION`) through that shared path, so the list write check, multi-VTODO component handling, search index, #2172's task change set, #798's status notification logic and #2173's activity writer all run, exactly as for a REST `PATCH`. The state tag is the precondition instead of the object `If-Match`.
  - **A blank title is never saved.** A blank or whitespace-only `title` gets `422 title_required` (`TaskPatchRequest` requires `min:1` today). The client does not send one: see Client session, "Blank title".
  - The state row is written in the same transaction as the object, with the new `object_etag`, `content_etag` and an emptied chain. Writing the state row is the **last** write to the chain in that transaction, so no link of the text this save stored survives it.
  - The response is `200 {ok: true}` with `ETag` set to the new state tag. Errors use the shared envelope (`error`, `code`); clients classify on status and code only.
- OpenAPI describes the three operations, the framed body, and the `X-Wgw-External-Write` header on both sides.
- `PATCH /tasks/items/{taskId}` and `PUT /tasks/items/{taskId}` are unchanged. API callers that set `title` or `description` there keep working; the room sees their change as an outside write.

### Client session (text-fields shape)

- `DocsCollabUrls` gains `documentShape: "text-fields"`. With it:
  - **Seed** writes `note-title` and `plain-body` from the text into a throwaway document whose client id is `seedClientId("text-fields", title + "\0" + description)`, plus `task-text-meta.root` set to that id and `task-text-meta.base` set to the seeded text (`{contentTag, title, description}`). No TipTap editor is created. Two clients seeding the same text produce byte-identical updates.
  - **Empty** means neither `note-title` nor `plain-body` is in `doc.share`. The shared session decides "empty" with `isYDocEmpty`, which is `getXmlFragment("default").length === 0` (`docs-collab-utils.ts:156`). That call creates the `default` root, and a text-fields document always looks empty to it, so `shouldApplyImmediateSeed`, `shouldSeedOffline`, `markSeedDoneAfterSnapshot` and `isMeshDocumentHydrated` would seed a restored offline document again (duplicating or replacing the local text) and insert the fragment this design forbids. With `documentShape: "text-fields"` every one of those checks uses the shape's own emptiness test and never calls `getXmlFragment`.
  - **Save** sends `plain-body` as the document part and `note-title` as `title` (`noteTitleForSave` already does the title; once the type exists it returns `""` for a blank title). Text is sent as typed: no trim.
  - **Blank title:** while `note-title` is blank or whitespace-only, the client holds the save (title and description) and the field shows "A task needs a title", like the over-limit hold under Detail view. While the title is blank no rebase runs and nothing is saved, also when a re-read answers `204` or brings another root: the room keeps its document, and an outside edit that arrives meanwhile is picked up by step 1 or 2 below. Leaving the task with a blank title restores the stored `SUMMARY` with `restoreBlankTitle`:
    1. read the stored state and the chain (the two reads above). When the stored state has the live document's root (`task-text-meta.root`), merge the chain the room has not seen yet with `mergeOutsideChain`. With no state row, or a state with another root, this step only reads: step 2 rebuilds the document. Offline, skip the reads and use the stored state and chain the room read last (kept in IndexedDB with the document); the save that follows waits for the connection like any save; its `409` merges anything newer, and a `412` (the cached state tag no longer matches, for example because the row was dropped) goes through the shared reload-and-reconcile path;
    2. **with no state row, or a state with another root** (a task before its first save, after a move, after the chain cap dropped the row, or after another client rebased): run the rebase (Reconcile) with the local title taken from `lastSyncedText`, **whether or not** the server text differs from `lastSyncedText`, so a blank title is never a side of that merge. The rebuilt document starts from the server state, or from the seed of the server text when there is none, so its title is the server's title. A restore edit built on the seed of `lastSyncedText` would not work here: after a link or a dropped row the live document is not on that seed's lineage, and Yjs keeps an insert whose neighbours it lacks pending, so the title would stay blank. That rebase is the whole restore: it saves only when its merged text differs from the server text (the held description, for example), and steps 3–5 do not run;
    3. **with a state that has the live document's root:** clear whitespace typed into the title after the stored state with a normal local edit, so the field is truly empty. Then build a throwaway as `mergeOutsideChain` does (the stored state plus every chain link), with the client id `hash32("restore-title\0" + stateTag + "\0" + chainEndTag + "\0" + summary)`, where `summary` is the chain end's title (or the stored state's title when the chain is empty). That id is never the seed id of the deleted characters;
    4. in the throwaway, delete the whole title and insert `summary` at offset 0. This is not `plainTextOps`, which produces nothing for two equal strings; the new items are what make the title reappear in a document that already deleted it;
    5. encode against the throwaway's state vector before that edit, apply the update to the live document, and save through the normal `PUT` with `If-Match` on the state tag. The description that was held goes out with it.

    Two peers that leave blank build identical bytes, so the title appears once: in step 2 because the rebase is deterministic (Reconcile), in steps 3–5 because the throwaway and its client id are. In the rare case that the same restore was already applied (the person left blank offline, came back, blanked the title again and left again before any save), the update of steps 3–5 is a no-op; the client detects that the title is still blank afterwards and repeats steps 3–5 with the same inputs plus the suffix `"\0again"` in the client id. That second update is deterministic too, so two peers that both reach it insert the title once.
  - **Line ends:** outside text is normalised to `\n` before it is seeded or diffed, because a textarea reports `\n` only. A `DESCRIPTION` with `\r\n` from a native client is saved back with `\n`.
- **Outside write while a room is open.** `decideExternalWrite` returns `"prompt"` for Notes when local work is pending (`use-docs-collab-join.ts:238`). The text-fields shape never prompts: it calls `mergeOutsideChain(ydoc, storedState, stateTag, chain)`, which builds one throwaway document from the stored state and, **for each link in order**,
  1. gives the throwaway document the client id `hash32("outside\0" + stateTag + "\0" + previousLinkTag + "\0" + linkTag)` (`previousLinkTag` is `""` for the first link);
  2. applies `plainTextOps(previousText, linkText)` to each field that differs, where `previousText` is the previous link's text, or the stored state's text for the first link, and sets `task-text-meta.base` to the link's text;
  3. encodes the items this link added (`encodeStateAsUpdate(temp, stateVectorBeforeThisLink)`).

  The live document gets the stored state, then every link's update in order, with the publishable `EXTERNAL_REBUILD_ORIGIN`. Each link's update depends only on the stored state and the links before it, so every client and tab builds the same bytes. A client that already applied links 1..k applies them again as no-ops and adds k+1..n; a client that missed link 1 replays it. So two native edits a few seconds apart (Reminders changes the title, then the notes; or deletes a word and puts it back) end, on every peer, on exactly the last link's text plus the typing. The client then saves with `X-Wgw-External-Write` set to the last link's content tag.
- **How an open room learns about it.** The open task's `Task` push (or `/changes` poll) brings a new `title` or `description`. When that text is not the text the room last saved or loaded, the room re-reads `GET …/text?format=yjs` and **then** `GET …/text` (`mergeServerState`), in that order and never in parallel: the first repairs the chain under the lock, so the chain the second returns already ends on the object's text whenever no native write landed between the two. The stored state comes from the first, the `outsideChain`, its `stateTag` and the server text from the second; when that `stateTag` is not the state the first returned, the room reads both again. The pushed text is only the signal to re-read; it is never diffed against the stored state directly, because a peer that already applied an earlier link would insert that edit again. A save that races it gets `409 external_write` and does the same two reads. When the stored state has the live document's root, both paths end in `mergeOutsideChain`, so whichever comes first wins and the other is a no-op. When the re-read brings a state with **another root** (always), or finds **no state row** (`?format=yjs` answers `204`, for example after the chain cap dropped it) and the server text differs from `lastSyncedText`, the room runs the rebase (Reconcile) right away, also when it has no unsaved edit; otherwise an idle viewer would keep the old text until a reload. Never `mergeOutsideChain` and never a bare `Y.applyUpdate` across roots: that leaves the old items in place and shows the title and notes twice. The rebase **replaces** the document and saves only when it has something to save (below), so an idle room changes its text and sends no `PUT`. While the title is blank this paragraph does nothing (Blank title, above).
- **`plainTextOps(base, next)`** is a pure function in `text-editor-core/docs-collab`: a line-level diff (Myers) of the two texts, then a common prefix and suffix inside each changed hunk (the method `replaceNoteTitle` uses for one line), returning `insert` / `delete` operations at character offsets of `base`. No new dependency.
- **Reconcile** (join, reconnect, a `412` on save). Inputs: the local document (y-indexeddb), its root, the server text the document already reflects (`lastSyncedText` and its content tag, kept next to the document in IndexedDB), and the server's `?format=yjs` answer plus the `GET …/text` read after it (the order above). `lastSyncedText` follows `task-text-meta.base`, which the seed, each link `mergeOutsideChain` applies, and each rebase write: whenever that key changes in the live document, by this client or by a peer over the mesh, `lastSyncedText` becomes its text. Two local events also set it: a save that lands sets it to the saved text, and a re-read that loads a stored state with an empty chain sets it to that server text, also when the mesh already delivered that document. So a rebase never inserts an applied link, or a peer's rebase, a second time.
  - Server state with the **same root**: apply it (the CRDT merges); if flagged as outside write, `mergeOutsideChain`; save.
  - Server state with **another root**, or **no state**: rebase. Before it reads `localText`, the client keeps the live document's state vector. `merged` is a CRDT three-way merge: seed `lastSyncedText` deterministically, apply `plainTextOps(lastSyncedText, serverText)` with one client id and `plainTextOps(lastSyncedText, localText)` with another, merge both. Then build the new document. With a state, load it and apply `mergeOutsideChain` with the chain from `GET …/text`, so the document holds the chain end's text, which is `serverText` (the state alone holds older text, and offsets taken from `serverText` would hit the wrong characters). With no state, seed the server text. Apply `plainTextOps(serverText, merged)` with the client id `hash32("rebase\0" + base + "\0" + sha1(mergedTitle + "\0" + mergedDescription))`, where `base` is the state tag plus `"\0"` plus the chain end's tag (`""` for an empty chain), or the server text's content tag when there is no state, and set `task-text-meta.base` to the server text. Every input is deterministic, so two peers that rebase the same text build the same bytes. **Check before use:** before `plainTextOps(serverText, merged)` the candidate's title and description must equal `serverText`. When they do not (a native write landed and its hook or the repair has not appended it yet, so the chain stops short of the object), the client discards the candidate, publishes nothing, leaves `task-text-meta.base` and `lastSyncedText` as they were, and reads again; offsets taken from `serverText` would otherwise hit the wrong characters of an older text. That document **replaces** the live one: apply its update, then delete the items it lacks among those the live document held when `localText` was read (`adoptServerSnapshot` with that kept state vector as the loaded state vector, as `replaceDocumentWithExternalText` does, `docs-collab-external-write.ts:54-76`), with the publishable `EXTERNAL_REBUILD_ORIGIN`. A character typed or received after that read stays. Peers still on the old root receive both over the mesh and end on the same text once. The rebase saves only when `merged` differs from the server text: with a state, `If-Match` on the state tag and, when the chain is not empty, `X-Wgw-External-Write` set to the chain end's tag; with none, `If-None-Match: *` naming the server text's content tag in `X-Wgw-External-Write`. When `merged` equals the server text it sends nothing. The rebase moves `task-text-meta.base`, so on this client and on every peer that applies it, `lastSyncedText` becomes the **server text** the new document was built on, not the merged text: unsaved characters stay local edits, so a `409` or a dropped row before the save keeps them. When the save lands, the saving client sets `lastSyncedText` and its content tag to the saved text, as after any save; a peer learns it from its next re-read (the push of that save triggers one). The stored state's root always wins, so clients converge on one lineage.
- **Two tabs** of one browser share the y-indexeddb document and the cross-tab channel the shared session already has; they behave as two peers.

### Detail view and form

- `TasksDetailView` mounts the room through a new `useTaskTextCollab({ task, readOnly, username, displayName })`, modelled on `useNoteBodyCollab`: live API only, one room per open task, `holdTaskTextRoom(taskId)` while it is open so push sync knows the room leads.
- Unlike a note room, which makes push sync fetch the note **without** its body (`note-body-rooms.ts`), a held task room does not drop `title` or `description` from the inbound task: the room needs them to notice an outside write. They are kept in the cache but never written into the bound fields; the document owns what the fields show.
- It wraps the view in the existing `NoteCollabYDocProvider`, so the title (already rendered by `NoteDetailView`) binds to `note-title` with no Tasks code. The description `TextareaAutosize` binds through the generalised field hook with key `plain-body` and its own awareness field for carets (`noteTitleSelection` stays the title's field).
- `title` and `description` leave `TASK_DETAIL_SAVE_DEBOUNCE_MS` and `taskEditPatch` while a room is open or loading. The other fields keep the 600 ms autosave. Without the live API (mock, Storybook) the detail view behaves as today.
- While the room is loading, the fields show the stored text read-only, so nothing typed lands outside the document. This differs from Notes, which saves a title edit by `PATCH` while its document loads (`onTitleEdit` in `use-note-title-field.tsx`); for tasks that `PATCH` would come back as an outside write and be merged a second time.
- The list row shows the live title: the room projects `note-title` onto the in-memory task (`projectTaskTitle`, like `projectNoteTitle`) without a write or an outbox row.
- `rebaseTaskForm` (#1858) keeps working for the other fields. `title` and `description` drop out of its field groups while a room is open, because the document owns them.
- `maxLength` is 4 096 on the title and 8 192 on the description. A merge can still push a field over its limit (two people add at once). The field then shows its "too long" hint, the save is held, and the text is not cut; the next edit that brings it back under the limit saves.

### Outbox and autosave (disjoint-field retry)

- Online autosave (`use-task-detail-autosave.ts:244`) and the outbox flush (`tasks-outbox-flush.ts:126`) both send `If-Match`. On a `412`, the client fetches the task once and compares, **for each field in the patch**, the server value with the value the patch was based on.
  - None changed on the server: send the same patch again with the server's ETag. No dialog, no error.
  - One did: today's behaviour (the conflict dialog from the outbox, the error and revert from the autosave).
- The base values are recorded when the patch is made: the autosave has the task it diffed against; an outbox row gets a `base` map of the patched fields' previous values, kept through `coalesceTaskPatches` (the first base of a field wins). Rows queued before this change have no `base` and keep today's behaviour.
- `title` and `description` leave `TaskConflictFieldKey`'s rows for tasks with a stored state, because the document merges them. Old outbox rows that carry them still flush as they do today.

### Access loss and read-only

- A read-only peer binds both fields read-only, receives updates and carets, and publishes no caret.
- `onPersistForbidden` (a `403` on save) or a `404` (the task was deleted, or moved out of every list the person can see) while the room holds unsaved text: the client leaves the room, shows the fields read-only with the message "You no longer have access to this task. Your last changes were not saved here.", and parks the task with the document's text through `parkTask`, so the existing rescue view can create it in another list. The poll-side `403` from signaling does the same.
- A peer that loses access keeps its local copy of what it already received. That is the same gap Notes and Docs accept (Decision 8 of `notes.md`); nothing new is exposed, because the peer could read it a moment earlier.

### Activity log (needs #2173)

- #2173's `ThreadActivityWriter` merges an entry into the thread's **newest** entry when it is an activity entry by the same actor, for the same field, younger than 10 minutes.
- For `title` and `description` only, this Epic changes the rule to: merge into the **newest activity entry for the same field** when it is younger than 10 minutes and no comment or reply was posted after it, **whatever its actor**. The actor is added to a new `actors` list on the entry (the entry's author stays the first actor). `to` is updated for `title`; `description` stays a changed flag.
- If `from` then equals `to` and only one actor is listed, the entry is deleted, as #2173 already does.
- The client formatter renders "Anna and Bob edited the notes" and "Anna and Bob changed the title to 'Moodboard v2'"; three or more actors read "Anna and 2 others".
- Every other field keeps #2173's same-actor rule.
- If this Epic is built before #2173 lands, chunk E is a change to #2173's spec instead, and the rule goes in with #2173's chunk F.

## Edge cases

- **Two people type in the same sentence.** The CRDT keeps both. Each person's save carries everything merged so far; the second save of the same text changes nothing in the VTODO.
- **Someone edits the title in Reminders while two people type in the notes.** Both browsers see the new title within one push (or one save round trip). Both apply the same deterministic update; their notes typing is untouched. The next save stores the merged text with `X-Wgw-External-Write`.
- **Reminders changes the notes in the same place someone is typing.** The outside diff and the typing merge by the CRDT: both texts stay, interleaved at the character level where they touch. Nobody is asked. This is the accepted cost of never prompting.
- **An offline edit, while the text also changed elsewhere.** On reconnect the room reconciles: same root, it merges by the CRDT and applies the outside diff; other root or no state, it rebases with the three-way merge. Either way no prompt, and the save goes out.
- **Two tabs, one offline.** The offline tab's edits live in the shared y-indexeddb document and reach the other tab through it; the online tab saves them.
- **A status change while someone types.** The status patch gets `412` because a text save changed the ETag (also when it read the object before that save and reached its write after it: the locked `If-Match` check refuses it, and it writes nothing). Its field (`workflowStatus`) did not change on the server, so it is retried once with the new ETag and lands beside the saved text. If another text save lands between the refetch and the retry, the retry gets `412` too and today's error path runs; one retry is enough at a save every ~3 s.
- **A task moved to another list while a room is open.** The room key changes and the old state row is gone. The open detail view closes the old room and joins the new one, if the person can see the new list; a peer that cannot is told it no longer has access, and its unsaved text is parked.
- **A task in a multi-VTODO file.** The room and the state row are per component (`vtodo_uid`); a save rewrites only that component.
- **A recurring task.** Title and description live on the master, as for a REST `PATCH`. An override with its own `SUMMARY` from another client is left as it is.
- **A task created offline.** Until its create lands it has only a temporary id (`tempTaskId` in the outbox row), which the server replaces. Such a task opens **without a room**: its title and description edits go into the queued create through the existing outbox, as today. The room opens once the task has its server id. Unlike Notes, where the app picks the final UID up front, this keeps the temporary-id remap out of the collab layer.
- **The title is blanked.** The field shows "A task needs a title" and the save is held (the description waits with it, because one `PUT` carries both). Typing a new title releases the save, and `SUMMARY` becomes exactly the new title. If the person leaves the task while the title is still blank, `restoreBlankTitle` (Client session) puts the server's title back and saves it together with any notes that were waiting (with no state row and nothing waiting, the title comes back without a save); a peer still in the room receives it over the mesh, and a second peer that leaves blank builds the same bytes.
- **Two peers rebase onto different server texts at the same moment.** `task-text-meta.base` is one map key, so Yjs keeps one of the two values by client-id order, not by which came later. That converges: the stored state's root wins, and the peer whose base lost gets `412` on its next save and rebases again.
- **Two native edits a few seconds apart.** Reminders changes the title, then the notes, before any peer saved the first merge. Both edits are links of one chain, so a peer that saw the first and a peer that missed it end on the same text, and nothing is inserted twice or left deleted.
- **A completed or cancelled task** stays editable, as today. Tasks have no archive.
- **Search** indexes each save, as it does for a `PATCH`; while someone types that is one re-index per ~3 s per typist.
- **Push load.** Each save is a task write, so every client of that list gets a `Task` state change and fetches one task; a thread panel that is open refetches its thread. This is the same per-save cost Notes has, and the "Collab rooms lead" rule keeps the typing tab from refetching its own text.
