# One local file tree for Drive and Docs home

## Goal

Replace the per-view listing code of Drive and Docs home with one local recursive tree (`drive_entries`) that both apps query. Fetch that tree in a few batched JMAP requests, keep it current with `FileNode/changes` only, and make Docs home a configuration of the Drive workspace. Fix the three server gaps the design depends on: query cost, team membership in the change state, and share flags on FileNode.

## Budget

Draws from the Pioneer programme chore #2063 (Docs/Drive family of #1641) and from Epic #2284 (traffic budget): a Drive open stops costing one request per folder. Displaces the per-view cache direction that #2063 described before 2026-11-26, and the `docs_listing_rows` patching rules of `1563-docs-inbound-sync` decision 4 and 10. Does not displace #2338 chunk F (shared body queue).

## Non-goals

- Body or binary download changes beyond #2063's per-row indicator criteria.
- Offline full-text search.
- Moving Drive/Docs inbound onto the #1565 engine.
- Guest sessions.

## Considered

- **Docs keeps `GET /search/results` as its list route, made lean with a keyset cursor (option A of #2362 / PR #2383):** rejected for lists. It keeps two server routes, two permission models and a second offline cache. #2383's reasons against the FileNode route (no extension filter, no modified sort, no limit pushdown, no mtime column) assume server-side filtering; here filtering and sorting run on the device, so the server only pages the unfiltered tree. Kept from #2383: every list page goes through the background-sync pacer (chunk C1), and the lean snippet cut for full-text search results stays with #2362.
- **Per-view caches (the Docs model, the earlier #2063 direction):** rejected. It keeps one copy of the same rows per filter and needs its own refresh per view. One tree makes every view, including never-opened folders, available offline after one sync.
- **A server-side "tree snapshot" endpoint (one JSON of the whole tree) or a Sabre plugin that writes a tree record on every write:** rejected. `jmap_file_nodes` already is that record, kept current by `FileNodeIndexPlugin` and `DriveService`, with `FileNode/changes` for deltas. A second representation would need its own invalidation.
- **The search index as list source:** rejected for lists. It is a full-text index, updated best-effort, and is the reason Docs and Drive diverged. It stays the source for content search.
- **Dexie `liveQuery`:** rejected in favour of the existing `cacheChangedTopic`, which every offline domain already uses and which crosses tabs.
- **Share flags as a separate client cache of the person's shares:** rejected. A FileNode property, filled by the existing batch lookup and propagated by a seq bump, keeps one sync path.
- **Position paging on the name sort, with a catch-up from the pre-page-1 state:** rejected after review. A node deleted, or renamed to sort later, before the cursor shifts every later position by one, so one unchanged node lands on no page; `FileNode/changes` never reports it because it did not change. Restarting the pass until `queryState` is stable does not terminate either: the sequence is global, so any account's write changes it. The walk pages by a `node_id` keyset instead (chunk S1), which a delete or rename cannot shift.
- **A snapshot table for the paged walk:** rejected. The keyset plus a catch-up with `FileNode/changes` gives the same result with no extra server state.
- **Team join/leave as a server-emitted subtree of created/destroyed:** rejected for now. Adding the root set to the state hash reuses the existing `cannotCalculateChanges` → full resync path, which is cheap after chunk S1.

## Chunks

### Chunk S1: cheap paged tree read
- **Skill:** api
- **Inputs:** reconcile on every unfiltered query — `path: packages/api/app/Services/Jmap/Methods/FileNodeQueryMethod.php:159`; full models loaded — `path: packages/api/app/Services/Jmap/FileNodes/FileNodeIndexService.php:156`.
- **Done when:** `FileNode/query` accepts two top-level arguments next to `position`, `limit` and `depth`: `idAfter` (a `node_id` keyset, run in SQL as `ORDER BY node_id` and `node_id > idAfter`) and `asOfState` (only nodes with `created_seq` at or below that state's sequence and `deleted_at` null). `id` is added to `SUPPORTED_SORT_PROPERTIES` (`FileNodeQueryMethod.php:28`). A query with no filter keeps the unfiltered scope (home, teams, share roots): the keyset `WHERE` keeps the caller's visible roots, the same set as `liveVisible`, so `node_id > idAfter` never walks other accounts. Because `idAfter` is top-level, the existing dispatcher resolves `#idAfter` (RFC 8620 §3.7, `JmapMethodDispatcher.php:257`), so one request chains query+get pairs, each query referencing `/ids/499` of the previous one. `asOfState` is resolved the same way from the `/state` of a `FileNode/get` with an empty id list at the start of the first request, so that request holds the state get plus 15 pairs. A keyset page is returned in `node_id` order and is not passed through `sortNodes` (`FileNodeQueryMethod.php:222` defaults to name), so `/ids/499` is the greatest id on the page. An `asOfState` whose grant hash no longer matches the current grants is still honoured by sequence; the client's catch-up from that state then returns `cannotCalculateChanges` and the pass restarts. `FileNode/get` returns `path`, the node's virtual path (`/` plus the storage key, the inverse of `StoragePaths::virtualToStorageKey`), for account roots, share roots and every descendant. The capability advertises the keyset and `path`. No `FileNode/query` without a `parentId` or `ancestorId` filter reconciles against disk, keyset or not (decided 2026-11-26: writes through the app keep the index current; the open folder, get-all and the reindex command heal drift), and the unfiltered query loads only the columns it sorts and filters on. On the 20,440-node bench a page costs at most 300 ms and a constant number of SQL queries. Feature tests from the Invariants pass. The throwaway bench is not committed.
- **Verify with:** `php scripts/done-gate.php` (or CI shards), the two S1 invariant tests.
- **Parallel with:** S2, S3, C1

### Chunk S2: team membership and arrivals in the change state
- **Skill:** api, security
- **Inputs:** state hashes grants only — `path: packages/api/app/Services/Jmap/FileNodes/FileNodeAccountSupport.php:98`, `path: packages/api/app/Services/Jmap/FileNodes/FileNodeSyncState.php:10`.
- **Done when:** the state carries a hash over the sorted account root set plus the grant pairs (hash the set whose change must be detected, review-findings 2026-11-04). A join or leave yields `cannotCalculateChanges`. Push state follows the same roots. Old states decode as `cannotCalculateChanges`. `changesSince` also reports arrivals, mirroring `destroyedSince`: a node whose first departure after `since` has a `from_key` the caller could not see, whose current key is visible, whose `created_seq <= since`, and whose `deleted_at` is null is listed in `updated`, so a node never appears in both `updated` and `destroyed`. The same holds when that `from_key` is not a list path (any segment starting with `.` other than `.Trash`, the C1 row rule) and the current key is one and visible to the caller: a folder moved out of `.notes` or `.attachments` brings its descendants. The departures table already holds every moved descendant (`FileNodeDepartures::record`), so this is one query. Today `recordMove` bumps only the moved node (`FileNodeIndexService.php:402-423`), so a folder dragged from home into a team drive reaches other members without its children.
- **Verify with:** S2 invariant tests; existing `TeamHiddenDriveSharesTest` stays green.
- **Parallel with:** S1, S3, C1

### Chunk C1: tree sync replaces the crawl
- **Skill:** workspace, client-transport
- **Inputs:** crawl — `path: packages/apps/src/lib/offline/drive/drive-metadata-sync.ts:101`; callers — `path: packages/apps/src/drive-core/src/use-drive-api.ts:59`; inbound — `path: packages/apps/src/lib/offline/drive/drive-inbound-sync.ts:182`.
- **Done when:**
  - `syncDriveTree` walks the tree with the S1 keyset (`FileNode/query` + `FileNode/get` pairs, each query chained by a top-level `#idAfter` reference to `/ids/499` of the previous query; the first request starts with the state get and passes `#asOfState` from its `/state`, so it holds 15 pairs and later requests 16), including Trash and share roots, under the Web Lock, with the last `node_id` as resumable cursor and a `firstSyncDone` meta flag. On a server without S1's keyset it keeps the per-folder crawl and never pages by `position`; the crawl never sets `firstSyncDone`.
  - **End of walk.** The walk ends only when a `FileNode/query` succeeded and returned fewer than `limit` ids; the `invalidResultReference` errors after it in the same request are ignored. A page is staged only when its query and its get both succeed, and only the prefix of the request before the first failed query or get is staged; pages after a hole are discarded, even when they succeeded. The cursor advances only through that prefix, so a retry starts at the page with the hole. Any such error keeps `drive_entries`, does not prune, and stores no token.
  - **Paths.** During the walk, each page is upserted into `drive_entries` at the `path` that `FileNode/get` returns (S1), so rows that already arrived show. The final paths are resolved once, after the catch-up, from the staging table: a node whose parent is staged gets the parent's resolved path (never the parent's stored server path, which is stale under a renamed ancestor) plus its own `name`; a node whose parent is not staged (account root, share root) keeps its server `path`. The resolver treats a repeated id in a chain as a cycle and skips that row instead of hanging; a deep acyclic chain is kept. The resolved `path` and `name` are written into the entry body before the upsert, since the row is keyed on `entry.path`. This is order-independent, so nested renames during the walk resolve correctly, and two share roots with the same name keep their distinct server paths. `parentId` also decides `area`.
  - **Walk staging.** Each staged page is also recorded in a staging table keyed by `node_id` (`parentId`, `name`, server `path`, entry data), dot-path nodes included. The staging rows are the persisted walked set, so a resume after an abort still has every page fetched before it. When a pass starts, before page 1 is upserted, the pre-pass `nodeId → path` map of every `drive_entries` row is persisted beside the staging table; a resume reuses it, and so does a restart after `cannotCalculateChanges` (no sidecar has moved yet); it is deleted by the crawl fallback, and replaced in the same transaction that moves the sidecars by the final `original path → final path` map for the page-setup write below, so a committed move never replays. A pre-pass path is a source only while no other node's row holds it; a node's current row paths are sources too. When a node has more than one source path that holds a blob, the pre-pass path wins. A page upsert inserts a node the pre-pass map does not contain, and replaces a row only when its path and its `nodeId` both match; a node the map already has stays at its mapped path until the pass commits, so a half-finished walk never forks a node onto a second path or pairs one node's entry with another node's blob. When `drive_entries` holds one `nodeId` at two paths, the map takes the row that holds the blob. The staging table is cleared when a pass finishes or restarts.
  - **Snapshot rule.** The state from the first request's state get is stored with the cursor. Every query passes it as `asOfState`, so the walk returns only nodes that existed at that state (S1). A resume reuses the same state. After the last page it applies `FileNode/changes` from that state to the staging set: `destroyed` removed, `created` and `updated` fetched and written to the staging table (new `parentId`, `name`, `path` and data). `recordMove` bumps only the moved node, so unchanged descendants keep their staged `parentId` and follow their parent through the path resolution above. The client then resolves every staging row's final path and applies the dot-path filter; the remaining rows are upserted into `drive_entries` at their final paths only after the sidecar relocation below, which also adds a child that was never a list row before (a folder moved out of `.notes`). Relocation reads its original paths only from the pre-pass map, never from `drive_entries` after pages were upserted. It reads every blob, drive availability row, docs availability row and page-setup override (the set `applyDriveSidecarPathMigration` moves) from those original paths, writes them at the final paths, and only then upserts the staging bodies. Page-setup overrides live in `localStorage`, so they are applied once from the final map after the IndexedDB transaction commits, not through `moveDocsPageSetupOverride` one call at a time. The final map stays persisted until that write finishes and is then deleted; an open that finds a final map left by a stop applies it before it syncs. The write is idempotent, so applying it twice is safe. This is the same two-phase relocation as the steady-state applier, never the one-row helpers, so a nested rename never leaves a blob on the outer path and two files that swap during the walk keep their own bytes. Every source key is read before any clear. After the copy and before the prune, the blob and availability rows at each final path of a staging row are removed in that transaction when nothing was read for that row, so a never-downloaded file that lands on a downloaded file's old path does not show its bytes. The page-setup override at such a path is removed in the `localStorage` write from the final map, which records these clears so the open that replays a leftover map replays them too. Paths that no staging row lands on are left to the prune. The applier and the catch-up fetch `updated` and `created` in batches of `maxObjectsInGet`, since a large subtree can arrive at once. A node created and deleted during the walk is never stored. Only when that call succeeds does it prune, and its `newState` becomes the account token; the same write sets `firstSyncDone`. The keep set is the final resolved paths of the staging rows left after the catch-up and the dot-path filter, plus `prunerProtectedPaths` and their ancestors (outbox paths and upload placeholders) and the pending server saves that `dropMissingRow` keeps (`drive-fetched-set-prune.ts:174`); every other path is deleted, so the old path of a moved node and a row moved under `.notes` both go. On `cannotCalculateChanges` (a pause past the tombstone horizon, a grant change, or a team join or leave after S2) it keeps the existing `drive_entries`, stores no token, does not prune, clears the staging table, and starts a new pass with a new starting state.
  - **Row classes.** A node is not a list row when any segment of its path starts with `.`, except `.Trash`. The rule applies in the tree walk and in the `FileNode/changes` applier, to every final path, including cached rows the applier prefix-replaces under a moved folder, so files inside `.notes` and `.attachments` are never stored and an existing row moved into one, with its cached descendants, is removed. `area` (`home | group | share | trash`) is computed after that filter.
  - **Share flags.** `FileNode/get` requests `shareFlags` when the server advertises it (S3). `hasShares`, `hasPublicShare` and `hasTeamShare` are stored on the entry, and the badge reads that copy. Without S3 the rows simply have no flags.
  - Every listing request waits for the background-sync pacer at `first` priority, so the first sync never sends unpaced list pages (requirement taken from #2362 / PR #2383).
  - One new Dexie version holds the whole schema change: rows gain indexed `ext` and `area` (`home | group | share | trash`), backfilled from `data`, and the walk staging table is added.
  - App open, reconnect and settings change call `FileNode/changes` only. The full sync runs with no token, on `cannotCalculateChanges`, or when `firstSyncDone` is unset while the server has the keyset (also when a token exists, as on every device that synced before the walk). The crawl stores its token but never `firstSyncDone`, so a server without the keyset crawls only on a missing token or `cannotCalculateChanges`, and a crawled device walks the tree once the keyset appears.
  - **Steady-state applier uses the same paths.** `applyFileNodeChanges` first snapshots each updated node's cached path. It resolves `created` and `updated` like the walk: the parent's final path plus `name`, or the `FileNode/get` `path` when the parent is not in the tree (share roots); a repeated id is a cycle and that row is skipped. Each `created` or `updated` id stays at its resolved path, even when that path lies under another node's old path. Every other cached row gets the single longest snapshotted prefix applied once, matched on the original paths with a segment boundary (`old + '/'`), and its `id`, `parentPath` and `data.path` are rewritten (a child keeps its `name`). This builds one final map from original path to final path for every relocated row, `created` and `updated` ids included. Relocation runs in two phases: first every blob, availability row and prefix-replaced local entry is read from the paths as they were before this batch, then each is written at its final path, and only then are the `created` and `updated` entries from `FileNode/get` written. The one-row-at-a-time helpers (`migrateDriveContentBlobPath`, `migrateDriveAvailabilityPath`, `migrateDriveEntryPath`) are not used here. So a renamed download keeps its bytes and two files that swap paths keep their own. After the writes, at each final path of a row in this batch, a blob, availability row and page-setup override stay only when they were read for that row; a final path whose row had nothing to read is cleared, so a file that lands on a path never keeps the previous file's offline bytes. The clear covers only final paths of rows in this batch: a download the batch does not relocate keeps its blob. A path is deleted only when no surviving row's final path is that path; this includes a `destroyed` id's cached path. A destination that is not a list row (Row classes) is deleted, not written. The occupant check runs on the final map before any write: a kept unsaved document that is not in the batch blocks, and one that this batch relocates is not an occupant. On `blocked`, no row, blob, availability row, page setup or Docs change is written, and the token is not stored, so the next sync retries. A `destroyed` id whose cached path has unsaved local work has two outcomes. When no other row's final path is that path, it keeps its row, blob, availability and collab database, is recorded with `rememberKeptUnsavedDocuments`, and the token is stored. When another row's final path is that path, the destroyed document is an occupant: the batch blocks before any write, writes nothing, does not prune and stores no token. The same check runs in the walk before its sidecar write and final upsert. Until C4, the Docs `moved` changes are built from the same final map: one `moved` per relocated file, from its original path to its final path. `planDocsListingInbound` resolves a batch against the view from before the batch: it reads each source row once, writes it only at its own `to`, and does not prefix-expand with `startsWith(from + '/')`; a `to` that is also a `from` in the batch is never read back. After the writes it removes every `from` and every destroyed path that is not some row's `to`. A row that `docsRowOwnedByQueuedWrite` owns stays. The `movesSince` changes of `fullResync` go through the same batch rule. Starred paths, path-keyed collab databases and the open editor follow the same final map, not one `moved` event at a time (C7): each is read once from its path before the batch, written only at its own final path, never prefix-expanded with `startsWith(from + '/')`, and never read from a path that is also a `from`; a destination collab database receives the source state alone, and a starred path or path-keyed database whose path is not a surviving final path is deleted only after those writes. The editor gets one `publishDocsPathMoved` per open document, from its original path to its final path. This runs before the prune, and the prune never deletes a path-keyed collab database of a node that still has a row. Creates and in-place updates stay `upserted`, and a `destroyed` id whose cached path is not a surviving final path stays `removed`. This replaces the `migrateDriveEntryPath`-per-node order and `moveCachedNodeToPath`, which break on nested renames, renames onto a vacated name and swaps in one batch.
  - The BFS crawl is no longer the sync path: it stays only as the fallback for a server without S1's keyset, and a device that only ever crawled walks the tree once the server offers the keyset. The full resync (`fullResync`) uses `syncDriveTree` and keeps calling `applyDocsInboundChanges(movesSince)`, so a renamed Doc keeps its star, its local text and its open editor; that call follows the batch rule of the steady-state applier (C7).
